Choosing the right scaffold

The scaffolding decision matrix.

There is no single best pedagogy — only the best pedagogy for this concept, with these students, at this point in their development. Match the learner's need to the technique that fits it. Then plan to fade the scaffold as competence grows.

The need Students are meeting a brand-new concept for the first time and have no working mental model yet.
Unplugged + worked example Build the concept in everyday language. Then a fully solved code example with subgoal labels.
The need Students can describe the concept but can't yet read code that uses it accurately.
PRIMM Predict → Run → Investigate → Modify → Make. The predict-first habit forces engagement before guess-and-check.
The need Students can read code and trace it, but need practice applying the concept in new contexts.
Use-Modify-Create Hand them a working program. Modify it. Then create a similar one of their own. Ownership shifts gradually.
The need Students are tackling a multi-step Scratch project and need a roadmap for engaging with example code.
TIPPSEE Title, Instructions, Purpose, Play, Sprites, Explore, Extend. A reading-comprehension lens for example projects.
The need The problem is too big to hold in one head. Cognitive load is choking student progress.
Decomposition + checklists Break the problem into named subgoals. Provide a checklist. Mark complete as each subgoal lands.
The need A student is stuck and frustrated. Their confidence is going faster than their understanding.
Pair programming Pair them with a peer. Driver/navigator roles. Talking through the problem aloud is half the cure.
The need Students have learned a construct but their code is shallow — they used it once, mechanically.
Creative coding within constraints An open project with required constructs. Students bring themselves in; the constraints ensure depth of practice.
The need Students need to see the concept across multiple contexts to abstract it.
Analogous representations Show the same algorithm in pseudocode, Scratch, and Python. Have students see the structure beneath the syntax.
The need Students with diverse abilities and prior preparation in the same classroom.
Universal Design for Learning Multiple means of engagement, representation, and expression. Multiple entry points to the same project.
The need Students are debugging and don't know where to start.
Debugging detective questions "What did you predict? What happened? Where did they differ?" A scripted self-questioning protocol.

Research-backed pedagogies

Scaffolding frameworks that actually work.

Decades of research and classroom practice have produced powerful, well-tested approaches for teaching programming. These pedagogies appear throughout the book.

UMC

Use → Modify → Create

A learning progression where students first explore an existing program, then modify it bit by bit, before creating their own original work. Ownership gradually shifts from teacher to learner.

A carefully sequenced approach where students first predict what code does (without running it), then explore, modify, and finally create their own. Builds code reading habits and conceptual understanding.

Chapter 7
For curriculum writers

8 principles for designing CS curriculum that actually works.

A curriculum is not a list of topics — it is a sequence of experiences designed to move students from misconception to mastery. These are the design principles that distinguish curricula that produce real understanding from curricula that produce running code with brittle foundations.

01

Design against misconceptions, not just toward concepts.

Every concept arrives pre-loaded with wrong intuitions students bring from everyday speech and mathematics. A curriculum that only teaches "what variables are" leaves those intuitions intact. The most effective curricula anticipate the misconception, surface it deliberately, then design specifically to replace it.

In practice
  • Open the variables unit with an unplugged Story Variables activity that surfaces what students already think about quantities that change.
  • Choose the whiteboard metaphor (one value, erased before write) over the box metaphor that suggests storing multiple things.
  • Include at least one multiple-choice item that traps the known misconception — your students' answers tell you whether the lesson worked.
02

Spend more time reading code than writing it.

Research consistently shows that code-reading ability correlates strongly with code-writing ability. Most beginner curricula reverse this and rush students into writing. The strongest pedagogies — PRIMM, Use-Modify-Create, worked examples — all begin with reading and predicting.

In practice
  • Open every new concept with an example program that students predict the output of before running it.
  • Make "explain what this code does" a graded skill, not a side activity — code tracing is foundational.
  • Build in Parsons problems (rearrange given code) before free coding to let students focus on structure without syntax overload.
03

Plan across four levels of abstraction.

A program exists at four levels: the Problem (what's the idea?), the Algorithm (the plan in plain language), the Program (the code), and the Execution (what actually happens when it runs). Students who can only think in code produce shallow understanding and brittle debugging skills.

In practice
  • Every project planning template has separate sections for problem statement, algorithm, code structure, and test cases — students fill them out before coding.
  • Pseudocode and flowcharts are explicitly taught as bridges between algorithm and code, not skipped over.
  • When a student is stuck, ask "which level is the problem at?" before suggesting code changes.
04

Scaffold heavily, then fade deliberately.

The first lesson of a unit should be so supported that almost any student can succeed. The last lesson should have them working close to independence. The arc between them is the curriculum. Scaffolds that never come down create dependence; scaffolds that come down too fast create dropout.

In practice
  • Lesson 1: worked examples with subgoal labels, teacher live-coding, pair programming required.
  • Lesson 2: PRIMM activity with most code provided — predict, run, investigate, modify.
  • Lesson 3: Use-Modify-Create with substantial starter code and a target outcome.
  • Lesson 4: Open project with constraints — choice of theme, fixed required constructs.
  • Lesson 5: Open project with peer feedback; scaffolds available on request.
05

Build formative feedback into every session.

You can't course-correct what you don't measure. Curriculum without designed-in formative assessment is curriculum that drifts. Every lesson should have at least one moment where students reveal what they're actually thinking — and the next lesson should be shaped by what you saw.

In practice
  • Exit tickets with one or two targeted multiple-choice items aligned to the day's concept (and to known misconceptions).
  • Mid-lesson code-trace activities students complete and submit before moving on.
  • Code reviews where pairs explain each other's projects — speaking aloud surfaces gaps in understanding.
  • A written record of which misconceptions you observed, used to redesign tomorrow.
06

Connect to student identity, culture, and interest.

Students who see themselves in the curriculum engage; students who don't disengage. This is not cosmetic. It determines who gets to become a programmer. A curriculum that allows real choice — of theme, of audience, of community problem — is a curriculum that includes everyone.

In practice
  • Project briefs are "creative constraints" — required constructs are specified, but theme, characters, and audience are chosen by the student.
  • Worked examples include the names, faces, and concerns of the students in your classroom — audit your materials for representation.
  • At least one project per unit invites students to address a problem in their own community.
  • Showcase events include families and community members as the audience.
07

Make bugs the curriculum.

The single biggest predictor of student frustration in CS is the silent assumption that bugs mean failure. Curricula that hide bugs, punish them, or treat them as something to "fix and move on" produce brittle learners. Curricula that make bugs the most interesting thing in the room produce resilient ones.

In practice
  • A "buggy wall" or "favorite mistake of the day" segment in every class.
  • Teacher live-coding deliberately includes bugs to surface debugging strategies in real time.
  • Debugging is taught as a named skill with explicit strategies (line-by-line trace, decomposition, comparison to working examples).
  • At least one assessment item per unit involves identifying and fixing a bug.
08

Pilot with real students, then iterate.

A lesson that reads beautifully on paper often falls apart in class. A curriculum is not done when it's written — it's done when it works for the students it was written for. Treat curriculum revision as ongoing, evidence-driven, and never finished.

In practice
  • Pilot every new lesson with a small group of students before rolling out to all sections.
  • Maintain a misconception catalog from real student artifacts — exit tickets, code submissions, recorded conversations.
  • Schedule explicit revision cycles after every unit, with documented changes and rationale.
  • Invite teachers who will use the curriculum into the design process — what they see in their rooms is data.
Worked example

A complete lesson, annotated.

The principles above, applied to a real 5th-grade lesson introducing variables. Every phase is annotated with what students do, what the teacher does, and what's being assessed. Adapt freely — the structure is the point.

Sample lesson · Apply the framework

Introducing Variables — 5th grade, 45 minutes, Scratch

Grade band: Upper Elementary (4–6) Environment: Scratch 3 Prior knowledge: Sequences, loops, basic sprite motion
Learning goals
  • Recognize that a variable stores a single value at a time, with a name we can refer to.
  • Distinguish a variable's name from its value.
  • Use a variable in a Scratch program that updates over time inside a loop.
  • Predict the value of a variable after an assignment (foundational for trace fluency).
01
Hook · Whiteboard variable
5 min

Teacher does: Writes my_num = 5 on a small whiteboard. "Add 2 to my_num. What's the value now?" When a student says "7," the teacher erases 5 and writes 7. Repeats: "Subtract 3." Erase. Writes 4. "Set my_num to 10." Erase. Writes 10.

Students do: Call out values. Notice that the name stays the same and the value changes. Notice that the old value is gone.

Designed against: The "box that holds many values" misconception. The whiteboard makes the single-value, erase-on-write property visible.

Assessment: Listen for "the old number is still in there somewhere" — that's the misconception you need to address head-on.

02
Model · Live-code the Counting Cat
10 min

Teacher does: Projects Scratch. Creates a variable named Number. Asks the class: "What value should it start with?" Sets it to 0. Drags a loop. Inside, drags say (Number) for 1 second, then change Number by 1. Runs it. The cat counts up.

Then deliberately introduces a question: "What if I swap the order — change first, then say?" Asks the class to predict. Then swaps and runs. The cat now counts from 1, not 0. Names the subgoals out loud: "First we initialize. Then we display. Then we update."

Students do: Predict, watch, react. Notice that order of operations matters. Begin to internalize the subgoal labels.

Designed against: The "code is just sequential" misconception that erases the importance of when a variable is read versus updated.

03
Guided practice · PRIMM Counting Cat
10 min

Students do: In pairs, receive a shared Scratch project with three Counting Cat variants. For each: Predict the output on paper. Run it. Compare. Investigate why predictions failed. The variants:

Variant A: Counts 0–9 by 1. (The base case.)
Variant B: Counts 0–18 by 2 (uses change Number by 2). Pairs predict — many predict 0–9 because they didn't notice the 2.
Variant C: The variable is never initialized in the script (Scratch defaults it to 0, but if the project was run before, it starts wherever it left off). Re-runs may produce surprising starting values.

Teacher does: Circulates. When a pair gets a "wrong" prediction, asks "where exactly did your prediction diverge from what happened?" Doesn't reveal the answer.

Assessment: The written predictions are formative data. Collect them. The Variant C surprise is the seed of the next lesson on initialization.

04
Productive struggle · Score-keeper
15 min

Open task (with constraints): "Build a Scratch project where a sprite earns points for something. The score must be a variable. The score must change in response to something happening on screen."

Multiple entry points:

· Blank canvas for students ready to design from scratch.
· Starter project with sprites placed but no score variable, for students who need a leg up.
· Exploded code — the necessary blocks scattered on screen, students assemble them, for students who need maximum scaffolding.

Pair programming required: One driver, one navigator. Switch roles after 7 minutes. The teacher walks around, asks "show me how the score changes — what triggers it?" When a pair is stuck, asks "what does your variable hold right now? What do you want it to hold?"

Designed against: The temptation for the teacher to fix bugs for students. Productive struggle is the point.

05
Showcase + exit ticket
5 min

Showcase: Two pairs randomly selected to share. Each pair shows what works and a bug they hit. Class gives "two stars and a wish."

Exit ticket — one targeted multiple-choice item:

set steps to 10
move steps steps

"After this code runs, what is the value of steps?"
A) 0   B) 10   C) 20

The trap: Many students pick C, because they think "move steps steps" updates the variable. (It doesn't — the move block reads the variable; it doesn't write to it.) If a third or more of your students pick C, tomorrow's lesson needs explicit work on read-vs-write before moving forward.

This is the loop that closes the day. The exit ticket is data. The next lesson is shaped by what it reveals.

Lesson architecture

Anatomy of an effective CS lesson.

A research-backed structure for a 45-minute introductory programming lesson. The phases are intentional: each one does work the others can't. Skip the hook and you skip surfacing misconceptions. Skip the showcase and you skip the moment where students consolidate.

5 min
Phase 01 · Hook

Surface what students already think.

Open with an unplugged activity, a short story, or a question that pulls students' existing intuitions into the open. The point isn't to teach — it's to listen. Whatever misconceptions live in your room will surface here.

Do Story Variables, Simon Says, "what's changing in this story?", a buggy code prediction, a tiny role-play. Whole-class or pairs.
Avoid Skipping this phase to "save time." You're not saving time — you're moving forward without knowing what's in students' heads.
10 min
Phase 02 · Model

Show your thinking, not just your code.

Live-code or walk through a worked example with explicit subgoal labels. Narrate your internal dialogue: "I'm initializing here because…", "I'm using a variable because…". Make mistakes on purpose and fix them aloud — this is where you teach debugging.

Do Project the code. Label subgoals. Make and fix a deliberate bug. Pause to ask "what would happen if I changed this?"
Avoid Code without commentary. Polished, bug-free modeling teaches students that "real" programmers don't make mistakes. They do.
10 min
Phase 03 · Guided practice

Predict → Run → Investigate.

Hand pairs a code snippet. They predict the output on paper before touching the keyboard. Then they run it. Then they investigate why their prediction differed from reality. The disconfirmed prediction is where the learning happens.

Do Require written predictions before running. Use PRIMM-style worksheets. Pair students up. Walk around and listen.
Avoid Letting students skip the predict step. Without prediction, "run the code" becomes guess-and-check.
15 min
Phase 04 · Productive struggle

Open task with multiple entry points.

Now students apply the concept to something they chose. Pair programming is the default. Provide multiple starting points — blank canvas, exploded code, partial program — so every student can engage at their level. The teacher circulates, asking questions rather than giving answers.

Do "Show me, don't tell me." Ask "what did you predict would happen?" Encourage pairs to ask three peers before asking you.
Avoid Rescuing struggling students too quickly. Productive struggle is the curriculum — but it must be productive, not despair.
5 min
Phase 05 · Showcase + exit

Two students present. Everyone reflects.

Random-select two pairs to share work — including the bugs they hit. The class identifies "two stars and a wish." An exit ticket with one targeted multiple-choice item closes the loop: did the concept land? Tomorrow's lesson is shaped by tonight's exit tickets.

Do Equity sticks for selection. Celebrate the bugs. Collect exit tickets and read them tonight, not next week.
Avoid Cutting this phase when running short. If you cut anything, cut productive struggle by five minutes — never showcase.
The deeper learning framework

Programming teaches more than programming.

Successful programming classrooms attend to three interconnected domains of student growth — not just content knowledge, but also collaboration skills and the mindsets that fuel resilient learning.

C

Cognitive

Deep content knowledge, critical thinking, problem-solving, computational thinking — algorithms, variables, debugging.

I

Interpersonal

Collaboration and communication. Expressing ideas, working in pairs and teams, sharing work, giving feedback.

I

Intrapersonal

Beliefs, mindsets, persistence, self-efficacy. The growth mindset that lets students persevere through bugs and frustration.

Misconception-driven design

Design patterns for known misconceptions.

For every well-documented misconception in CS education, there is a tested teaching pattern that addresses it. Pair them in your curriculum. Each pattern below shows the concept, the specific wrong intuition students bring, and three moves: surface it, replace it, verify the replacement landed.

Variables
→
"A variable holds multiple values."
Surface

Show x = 5; x = 10. Ask: "What's in x now?" Listen for students who say "both 5 and 10" or "10, but 5 is still there."

Replace

Whiteboard metaphor: a small whiteboard holds one value. Writing a new value erases the old one. Avoid the "box" metaphor.

Verify

Exit ticket: predict the final value of x after a short reassignment sequence. Trap distractors that look like accumulation.

Assignment
→
"= means equality, like in math."
Surface

Show x = x + 1 and ask students to read it aloud. Those who say "x equals x plus one" reveal the misconception.

Replace

Read assignment right-to-left, narrating: "Evaluate the right side. Take that value. Store it in x, erasing what was there."

Verify

Trace a sequence of three assignments with shared variables. Students draw the whiteboard state after each line.

Loops
→
"The condition is monitored continuously."
Surface

Show a while x < 5 loop where x changes inside. Ask: "Exactly when does the loop check x?"

Replace

Role-play the loop. A student stands at the "check point" at the top. They only check when the loop returns to them — never mid-body.

Verify

Predict how many extra iterations a loop runs after its variable crosses the boundary mid-body.

Conditionals
→
"Multiple IFs are the same as IF-ELSEIF-ELSE."
Surface

Show two grade-assignment programs — one with cascading IFs, one with IF-ELSE-IF. Trace both with score = 92.

Replace

Demonstrate that with cascading IFs, the final value overwrites earlier matches. Conditions must be mutually exclusive or use ELSE.

Verify

Multiple-choice item with a cascading-IF bug. Students identify the issue and rewrite using IF-ELSEIF.

Functions
→
"Print and return do the same thing."
Surface

Show two near-identical functions — one prints, one returns. Show what happens when you try to use their output in another expression.

Replace

Print = side effect, the audience sees it. Return = hands a value back to the caller, so it can be stored or composed further.

Verify

Have students compose two functions: average(a, b) + 10. Only return works. The compile-or-runtime failure makes the difference visceral.

Recursion
→
"Calls evaluate outside-in."
Surface

Ask students to diagram the call stack of a simple recursive call. Many will start at the outer call and resolve outward.

Replace

"Subcontractor" role-play: each student stands when called, hires the next, sits only when their result is computed. Calls resolve inside-out.

Verify

Trace factorial(4) on paper showing the stack growth and the return path. Identify the base case.

Initialization
→
"Variables start fresh every time you run a program."
Surface

Have students build a Scratch quiz that adds points but forgets to reset on green-flag click. Run it twice. Watch the score carry over.

Replace

Teach initialization as a deliberate first move. Every variable, every program-start. Initialization is a named concept, not a side note.

Verify

Code-review checklist: "Is every variable initialized exactly once at program start?" Students audit each other's projects.

Event handlers
→
"Events run sequentially, like normal code."
Surface

Show two Scratch scripts on one sprite, both triggered by green-flag click. Predict which runs first. Reveal: they run in parallel.

Replace

"Each event is its own little program, waiting for its trigger. When the trigger fires, the event runs — independent of any other event."

Verify

Build a project where two events update the same variable. Predict the final value. (You can't reliably — that's the lesson.)

What to avoid

Curriculum antipatterns.

Some curriculum decisions feel productive but quietly undermine student learning. If your draft includes any of these, treat it as a flag to redesign. These antipatterns come up repeatedly in research on novice programmers — and in real classrooms.

✕

Writing code before reading it

Throwing students into "write a program that…" before they've seen and traced working examples. Almost guarantees guess-and-check coding and shallow understanding.

✕

Solo work as the default

Students sitting alone at screens for the entire period. CS is inherently social — pair programming should be the baseline, not the exception.

✕

Open-ended discovery with no scaffolds

"Just explore Scratch for the period." Minimally guided learning has been repeatedly shown to be less efficient than scaffolded approaches. Free play has a role — but not as the curriculum.

✕

Assessment only at the end

A unit test in week six is too late. Without formative feedback every lesson, misconceptions calcify. By the time you know there's a problem, fixing it requires undoing weeks of practice.

✕

The box metaphor for variables

"A variable is like a box that holds values." This single sentence produces years of misconceptions: boxes hold multiple things, retain old contents, accumulate. Use the whiteboard metaphor instead.

✕

Identical project briefs for every student

"Everyone make a snowman animation." Crushes student agency, identity, and engagement. Use creative constraints instead — specify the constructs, not the theme.

✕

Forever loops everywhere

Teaching forever + if-then-stop as the default looping pattern instead of structured repeat until or while. Produces tangled, hard-to-reason-about code that hides the loop's terminating condition.

✕

Fine-grained, bottom-up coding in blocks

Encouraging students to write many tiny scripts attached to separate triggers. Spaghetti results. Teach top-down planning and structured loops in any block-based environment.

✕

Skipping unplugged activities to "get to the real stuff"

The unplugged activity is the real stuff — it's where the concept becomes concrete. Skipping it means moving to code before students have a mental model strong enough to hold the syntax up.

✕

Hiding bugs from students

"Polished" worked examples that always work the first time teach students that real programmers don't make mistakes. They do. Bring the bugs into the open and use them to teach debugging.

✕

"Just give them the syntax" attitude

Treating concepts as obvious once the syntax is shown. Concepts like variables, recursion, and event handlers require deliberate, scaffolded conceptual work. Syntax is the easy part.

✕

Testing only the "happy path"

Curriculum that doesn't require students to test with invalid, edge-case, or unexpected inputs produces brittle programs and brittle thinkers. Test with negative numbers, empty strings, division by zero.

Equity by design

A curriculum is who it includes.

Inclusivity is not an add-on or a final polish. It's a property of how the curriculum is structured from the first principle to the last lesson. These are the concrete design moves that make a CS curriculum work for every student, not just the ones who already fit the mold.

↗

Multiple entry points into every project

The same project brief should be accessible to students at every level of preparation. Build each project to support at least three starting points so students can engage at the level that stretches them — without leaving anyone behind.

  • Blank canvas for advanced students
  • Exploded code (Parsons-style) for students assembling their understanding
  • Partial program with annotated TODOs for students needing more structure
  • Complete program to modify or extend for students still building confidence
≈

Identity reflection in every example

Audit your examples ruthlessly. Whose names appear in worked examples? Whose stories drive the projects? Whose problems are worth solving? The students who don't see themselves silently learn that CS isn't for them.

  • Names in examples reflect the diversity of your students' communities
  • Project themes connect to real student-community concerns
  • Worked examples include critical discussions of bias in technology
  • Role-model figures span genders, races, and trajectories into computing
↔

Collaboration structures, not solo defaults

The lone-coder stereotype is both inaccurate and exclusionary. Build collaboration into the structure of the curriculum so students experience CS as the social, communicative practice it actually is.

  • Pair programming with explicit driver/navigator roles and rotation
  • "Ask three peers before asking the teacher" as a classroom norm
  • Classroom experts list — every student is named as the go-to for something
  • Group code reviews with structured peer feedback protocols
⌂

Family and community as audience

Showcasing student work to authentic audiences is one of the most powerful drivers of engagement — especially for students from communities historically excluded from CS. Build it into the unit calendar, not as a one-off "demo day."

  • End-of-unit showcases with families invited
  • Projects that address real problems in students' local communities
  • Tribal leadership and elders consulted on curriculum for Indigenous students
  • Family programming nights where students teach their parents the project
⊕

UDL built in, not bolted on

Universal Design for Learning is most powerful when it's a property of the design phase, not a retrofit. If you have to add accessibility "for student X" later, the curriculum design itself has a gap.

  • Multiple representations of each concept (visual, verbal, physical, code)
  • Text alternatives for visual materials; verbal alternatives for written
  • Pacing flexibility — some students will need more time on the same goal
  • Screen-reader-aware environments where blind or low-vision students participate
✦

Joy as a design requirement

A curriculum that produces only "competent" programmers without producing students who want to keep coding has failed at its primary mission. Joy is not the reward for learning — it's the engine that makes the learning happen.

  • Real choice of project theme and audience in every unit
  • Scaffolded creativity — constraints that enable rather than restrict
  • Celebration moments built into every lesson (showcase, "favorite bug")
  • Physical movement, unplugged activities, music — the screen is not the only space

She has served on the National K–12 Computer Science Framework team, the ACM Education Advisory Committee, the CSTA standards taskforce, and the editorial board of ACM Transactions on Computing Education. The vision for this handbook took shape during her doctoral studies at Stanford, designing an introductory programming curriculum that drew on learnings from CS education research and the learning sciences.

How to use the book

For every teacher, at every stage.

New to teaching programming?

Read the book in its entirety. It will give you an enduring foundation in what you're teaching and how to teach it. Begin with four overarching “umbrella” chapters: K (Learning Goals), J (Programming Languages), N (Naive Conceptions), and F (Formative Feedback).

Tip: Pair each concept chapter with a pedagogy chapter. Read about variables, then read about scaffolding strategies. Read about loops, then read about debugging.

Already teaching CS?

Use the book as a reference. Read a chapter over a coffee break. Pull it off the shelf when planning a unit. You'll discover new ideas and have plenty of “aha” moments from the examples and pedagogical tips shared by 40+ experienced teachers and researchers.

Tip: The chapters reference each other extensively. Each chapter cross-references related concepts and pedagogies, so you can follow your curiosity through the book.

A curriculum designer?

Use the book to inform what topics to teach, in what order, and with what supports. Each chapter discusses what students typically struggle with — invaluable when designing a coherent learning progression for elementary, middle, or high school.

Tip: The book is programming-language agnostic. Examples appear in Scratch, Snap!, Python, Java, JavaScript, App Inventor, and more — but the foundational ideas transcend any single language.

A teacher trainer?

The book is ideal as a text in K–12 CS teacher-training programs. Each chapter is designed to be accessible and friendly to all teachers, drawing on research but written for practical, actionable use in real classrooms.

Tip: The book transcends geographical boundaries. With authors from the US, UK, Canada, Finland, Switzerland, Germany, and Australia, the ideas are deliberately portable across school systems.
